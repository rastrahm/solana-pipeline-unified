// MÓDULO SOLANA · PORTFOLIO SYSTEMS

SOLANA-PIPELINE
UNIFIED

Rust · Turbine → Bridge → NVMe Engine

Orquestador de aprendizaje que cablea red/FEC (mini-solana-turbine) con persistencia KV (nvme-state-db): colas acotadas, backpressure tipado y ciclo de vida medible — sin reimplementar el disco ni el shred.

Ver en GitHub Ver en GitLab
// 01 — CONTEXTO

Por qué este proyecto

Tras construir Turbine y el motor NVMe por separado, faltaba la pieza del medio: el pegamento de un validador — ciclo de vida, colas y fronteras de responsabilidad. Este crate es ese laboratorio: orquestación honesta, no un Agave en miniatura ni un tercer motor de I/O.

// 02 — TRES PILARES

Qué entrega el orquestador

// PILAR_01

Solo orquestación

Arranca y apaga Engine + Turbine. Llama APIs públicas; no abre WAL, no parsea shreds, no habla de O_DIRECT.

  • start / shutdown / flush
  • Path deps a hermanos
  • Roles fijos en .cursorrules
// PILAR_02

Bridge + backpressure

Cola acotada crossbeam: try_send tipado. Saturación → BridgeSaturated / PipelineStall, sin bloquear al productor.

  • Hilo pipeline-bridge
  • Claves learn/v1/
  • Flush ante cola llena
// PILAR_03

Ingest → Engine

Feature simd: Pipeline::ingest_bytes → shards en cola → Engine::put. Demo CLI y recovery al reabrir.

  • IngestOutcome medible
  • Recovery post-shutdown
  • Bench e2e Criterion
// 03 — BÚSQUEDA Y LOGRO

Qué se buscó y qué se logró

El objetivo no era un validador: era cerrar el cableado red→FEC→cola→disco con fronteras claras y números honestos de laboratorio.

SE BUSCÓ

Pegar dos crates reales

Entender cómo un TVU-like entrega estado a un almacén tipo AccountsDB sin mezclar responsabilidades ni duplicar lógica.

SE LOGRÓ

Pipeline e2e cerrado

Fases 0–8: stubs → deps → lifecycle → bridge → ingest → flush/recovery → CLI demo → benches Criterion.

SE BUSCÓ

Backpressure explícito

Colas acotadas, errores tipados y política de flush documentada — no “esperar forever” en el hot path del productor.

SE LOGRÓ

Lab medible y honesto

Claves learn/v1/, demo --demo, recovery verificable y benches que admiten que el WAL O_SYNC domina submit_durable.

// 04 — DECISIONES TÉCNICAS

Motivo detrás de cada choice

Cada restricción fuerza el patrón correcto: este crate orquesta; Turbine hace red/FEC; nvme hace disco. Si una fase pide WAL o parseo aquí, queda fuera.

Decisión Motivo / tradeoff
Solo APIs públicas de hermanos No duplicar FEC, arena, WAL ni SST; el aprendizaje es el cableado, no un tercer motor.
Persistencia solo vía Engine put/get/delete/flush; el orquestador nunca abre archivos de estado ni menciona O_DIRECT.
Cola acotada + try_send Backpressure tipado (BridgeSaturated / PipelineStall) en vez de bloquear workers de red indefinidamente.
thiserror en lib; anyhow solo en main Errores de pipeline tipados y zero-cost; bootstrap del binario con contexto flexible.
Features uring/simd reenviadas Mismo contrato que turbine: CI sin io_uring usa --features simd; default = ambos.
Claves learn/v1/… Convención educativa explícita: no fingir encoding de AccountsDB ni ledger real.
Analogía TVU / AccountsDB, no Blockstore Alcance acotado: estado KV tras FEC; ledger de shreds y replay quedan fuera.
Fases con autorización explícita TDD por gate; evita mezclar lifecycle, bridge e ingest en un solo PR opaco.
Sin unwrap/expect en src/ Producción tipada; panics reservados a tests y benches.

// 07 — FLUJO DEL DATO

De shred a Engine::put

Bytes sintéticos (o UDP vía turbine) entran al Pipeline, se reconstruyen con FEC, cruzan la cola del bridge y persisten en nvme — el orquestador solo mueve y gobierna.

01

Ingest

Pipeline::ingest_bytes (simd): parse + FEC.

02

Outcome

Reconstrucción + plan de forward (sin send en demo).

03

Queue

try_send a cola acotada; stall si satura.

04

Put

Hilo bridge → Engine::put (learn/v1/shard/N).

05

Flush

schedule_flush / recovery al reabrir data-dir.
